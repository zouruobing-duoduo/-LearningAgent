# 苏格拉底学习Agent - 开发经验沉淀

> 实际踩坑后提炼的经验，适用于对话型Agent / 教学系统 / 飞书机器人开发

---

## 一、专家经验

### 1. 对话型Agent状态保护三层防护架构

对话型Agent的状态保护需要三层防护：

1. **持久化层**：学习上下文（state+current_topic）写入文件，重启后恢复
2. **安全网层**：状态意外变为IDLE但current_topic仍在时，非指令消息自动恢复TEACHING状态继续教学
3. **意图识别层**：INTENT_PROMPT中明确规则——"我不清楚""你来说下""还有其他例子吗"等对话性消息识别为chat，只有"学习xxx""开始学习"才识别为start_learning

三层中任一层失效，其他层可兜底。

### 2. LLM意图识别防误判：对话性消息不应触发功能指令

LLM意图识别容易把用户的对话性回复（如"力的高效传递""我也不清楚""你来决策"）误判为start_learning。

**解决方案：**
1. INTENT_PROMPT中明确列出反例，强调"只有明确表达'我要学习xxx'才用start_learning"
2. 去掉容易混淆的中间意图（如continue），用安全网统一处理
3. 关键词快速路径只匹配精确指令，不做模糊匹配

### 3. 教学型Agent Prompt设计五要点

1. **内容充实性**：要求每轮至少3-5句实质讲解+具体例子，不能"先简短讲一个点"
2. **最少轮次保障**：Prompt中注入当前轮次（第N轮/至少6轮），代码层硬编码检查不足6轮时忽略TEACHING_COMPLETE标记
3. **延续性提问处理**：Prompt中明确要求"还有其他例子吗"类消息继续补充新实例
4. **深度要求**：要求揭示"为什么"的因果链，不能只停留在"是什么"
5. **结束条件严格化**：用户能自己解释、能举例、能回答变式问题才可结束

### 4. 闲聊模式必须携带上一轮对话上下文

用户在IDLE状态下的短回复（如"好的""可以""嗯"）是对上一轮Bot提问的肯定承接。如果闲聊模式不注入`last_bot_reply`作为上下文，LLM会把这些短回复当成全新对话开场，产生"话题断裂"体验。

**解决方案**：`_casual_chat`中将`context.last_bot_reply`作为assistant消息注入，让LLM看到用户在回应什么。

### 5. 考核掌握度需要明确的量化评分标准

LLM打分如果没有明确的分级标准，会"凭感觉"打分，分数缺乏一致性和可解释性。

**解决方案**：在EXAMINER_PROMPT中定义5级掌握度标准（1星=仅记住表面 → 5星=融会贯通），并列出4个评估维度（概念理解、应用迁移、辨析能力、推理深度），要求LLM严格按标准打分。

### 6. 教学图文混排架构：LLM标记 + 外部渲染 + 飞书富文本

教学中插入图片的架构设计：
1. **LLM端**：在Prompt中约定特殊标记（`[MERMAID]...[/MERMAID]`、`[LATEX]...[/LATEX]`、`[IMG_SEARCH:描述]`）
2. **解析层**：`reply_parser`用正则提取标记，调用外部免费API渲染为PNG（Mermaid.ink、codecogs）
3. **发送层**：上传图片到飞书获取image_key，用post富文本格式发送文本+图片混排
4. **降级策略**：任何环节失败都静默降级为纯文本，不影响教学内容

## 二、常见陷阱

### 1. 学习上下文必须持久化，内存状态不可靠

LearningContext（state、current_topic等）必须持久化到文件（`data/context_{user_id}.json`），每次状态变更调用`save()`。

纯内存状态在服务重启、代码部署后会丢失，导致教学中途被重置为IDLE，用户体验极差。启动时用`LearningContext.load()`恢复。

### 2. 服务重启时关键状态与对话历史的持久化策略区分

当代码部署需要重启服务时，所有纯内存状态都会丢失：
- **关键状态（state、current_topic）**：必须持久化，丢失会导致流程断裂
- **对话历史**：可以不持久化，LLM可以从system prompt恢复教学；持久化反而可能导致旧消息干扰

### 3. 飞书长连接事件订阅需手动点击保存

在飞书开放平台配置事件订阅后，**必须手动点击页面上的"保存"按钮**，否则配置不会生效。这是一个容易遗漏的操作步骤。

### 4. 飞书长连接消息重复推送需显式去重

飞书长连接（WebSocket）可能对同一事件重复推送。需要在消息处理层用`message_id`做显式去重：
- 维护一个已处理的`message_id`集合（set）
- 收到消息时先检查是否已处理过
- 设置合理的缓存上限（如200条）防止内存泄漏

### 5. 飞书机器人私聊权限必须开通

飞书机器人要接收私聊消息，必须在开放平台开通 `im:message.p2p_msg:readonly` 权限，否则私聊消息事件不会推送到机器人。

### 6. 飞书编号列表等格式化消息类型为post而非text

用户在飞书中发送编号列表、加粗等格式化内容时，消息类型为`post`（富文本）而非`text`。如果只处理text类型会**静默丢弃**这些消息，用户发了消息却没有任何反应。必须同时解析post类型：提取content中嵌套数组里所有`tag=text`的元素拼接。

### 7. 飞书"思考中"状态反馈只能用发送+撤回实现

飞书patch API仅支持卡片消息更新，普通文本消息无法原地修改。实现"思考中→实际回复"的状态替换，只能用"先reply一条思考中消息 → LLM处理 → DeleteMessageRequest撤回 → 再reply实际内容"的流程。`_reply_message`需返回message_id供后续撤回。

## 三、项目核心决策

### 诊断与教学流程分离
- **诊断阶段**：一次性完成，面向用户个人总体认知能力评估，结果存入用户画像
- **教学阶段**：持续进行，每个知识点直接进入教学，不再重复诊断
- 诊断结果（1-5级）驱动教学策略选择（语言风格、节奏、举例类型）

### 知识点话题单元与对话历史保留
- 一个知识点的教学→考核→掌握是一个完整话题单元
- 话题单元内对话历史保留，掌握后（EXAM_PASSED）才清空
- 禁止超时清空对话历史

### 教学交互节奏
- 一问一答：每次只发一个问题，等用户回复后再发下一个
- 禁止连续发多个问题

### 教学节奏防抢跑
- **严禁抢跑**：只回应用户当前回答的内容，不主动讲解用户还没回答的子目录
- **一轮一步**：每轮只推进1个子目录的教学
- COVERED标记收紧：只有用户实际参与讨论的子目录才能标记为覆盖

### 知识总结卡片7维度
考核通过后自动生成结构化知识总结，包含：核心定义、数学推导、直觉理解、关键要点、应用场景、易混淆点、**用户个人薄弱点与强化建议**（第7维度基于教学摘要+考核摘要+薄弱点记录三方数据生成）。
